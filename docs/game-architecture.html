2. 游戏生命周期

Phase 状态机

"lobby"
→
auto-start (≤30s)
→
"active"
→
GAME_OVER 指令
→

Lobby 阶段

  1. useGameInit.initializeLobby() — 创建 GM + AI 玩家 + 人类玩家
  2. 分配语音、获取头像、设置 gamePhase = "lobby"
  3. Auto-start（page.tsx L155-171）：一旦 isInitialized && gamePhase === "lobby" && nonHostPlayers.length > 0 → 立即调用 startGame()
  4. 安全超时：30 秒后 setAutoStarting(false)

startGame() 流程

  1. 防重入检查 (gameStartingRef)
  2. 分配角色和 stats（从 configuredPlayers）
  3. Script Kill：构建证据板 + 嫌疑人提示
  4. 设置 playerNotes（AI 角色的私密信息）
  5. 调用 launchOpeningRound(kickoffState)

launchOpeningRound() 流程

  1. setGamePhase("active")
  2. Scene 模式（有 openingSequence）：播放预设消息序列，每条消息之间有 delay
  3. 普通模式：
    • 发送 Host 问候消息
    • 调用 seedInitialPlayerReplies() — AI 角色初始回复（typewriter 显示）
    • 800ms 后自动发送 "[Continue]" 触发第一轮 GM 回复

⚠️ Lobby → Active 的 UI 切换

当 gamePhase === "lobby" 时，ChatArea 不渲染，显示 spinner。只有 gamePhase !== "lobby" && gamePhase !== "ended" 且 isGameChannel === true 时才显示聊天界面。

isGameActive = gamePhase !== "ended" — 控制输入框是否可用。

Step 1: ChatInputArea（UI 层）

// chat-input-area.tsx L164-182
handleSendRef.current = (override?: string) => {
  if (sendingLockRef.current) return;           // 🔒 500ms 防重复
  let text = (override ?? input.trim()).trim();
  if (!text) return;                            // 空消息阻断
  // 添加 [SAY] / [ACTION] 前缀
  sendingLockRef.current = true;
  setIsSending(true);                           // 显示 spinner
  flushSync(() => setInput(""));                // 清空输入框
  onSendMessage(text);                          // → 调用 handleSendMessage
  setTimeout(() => {
    sendingLockRef.current = false;
    setIsSending(false);
  }, 500);                                      // 500ms 后解锁
};

阻断条件：

  • sendingLockRef.current === true → 500ms 内重复发送
  • composingRef.current === true → IME 输入法正在组合（Enter 不触发 send）
  • sendDisabled === true → !isGameActive || effectivelyEliminated || isSending
  • Send 按钮额外检查 !input.trim()

Step 2: useHostRound.handleSendMessage（逻辑层）

// useHostRound.ts L152-200
const handleSendMessage = async (content, options) => {
  if (!content.trim()) return;                  // 空内容
  if (gamePhase === "ended") return;            // 游戏已结束

  // ⚡ 中断路径：isRoundInProgress === true
  if (isRoundInProgress) {
    pendingHumanMsgRef.current = content;       // 只保留最后一条！
    interruptRef.current = true;
    addMessage({...}, channelId);               // 消息会显示
    return;                                     // 不触发 AI 回复
  }

  addMessage({...}, channelId);                 // 消息立即显示

  if (gamePhase === "lobby") return;            // Lobby 不触发 AI

  // 🔥 创建 AbortController + 看门狗
  roundAbortRef.current = new AbortController();
  roundWatchdogRef.current = setTimeout(() => abort, 120_000);
  setIsRoundInProgress(true);

  try {
    // ... 构建 context → callHostStream → runSpeakerQueue
  } catch (error) {
    // toast 错误提示
    setLastFailedSendContent(content);
  } finally {
    clearTimeout(watchdog);
    setIsRoundInProgress(false);               // ✅ 必须恢复
    // 处理排队消息
    const queued = pendingHumanMsgRef.current;
    if (queued) setTimeout(() => handleSendMessage(queued, {skipAddMessage: true}), 100);
  }
};

🔴 isRoundInProgress 的关键行为

  • 设为 true：在 setIsRoundInProgress(true) 后进入 try 块
  • 设为 false：finally 块中，保证恢复（即使出错）
  • 卡住 = 一切停摆：后续所有消息走排队路径 → addMessage 但不触发 AI
  • 只保留一条：pendingHumanMsgRef.current = content 覆盖之前的排队消息
  • UI 影响：显示 "正在生成..." 脉冲指示器，但输入框不禁用

6. Speaker Queue 系统

SpeakerQueueItem 类型

type SpeakerQueueItem =
  | { type: "human" }              // 轮到人类说话 → 设置 currentSpeakerId = userId
  | { type: "everyone" }           // 所有人可以说话 → 2-3 个随机 AI 发言
  | { type: "ai"; player: Player } // 指定 AI 角色发言

runSpeakerQueue 流程

  1. 遍历 queue 中的每个 item
  2. "human"：设置 currentSpeakerId = userId → return true（humanReached）
  3. "everyone"：随机选 2-3 个 AI → 每个调用 speakAndReveal() → continue
  4. "ai"：跳过已淘汰玩家 → speakAndReveal(player)
  5. 夜晚阶段：跳过所有 AI 公开发言（私密频道单独处理）

speakAndReveal 流程

  1. thinkingDelay() — 80-400ms 思考延迟
  2. setTypingUsers([currentPlayer, ...upcoming]) — 显示打字指示器
  3. runPlayerSpeak() → fetch /api/chat/player-speak → AI 回复文本
  4. typewriterReveal(text) — 逐字显示效果
  5. triggerPassiveReactions() — 其他 AI 添加 emoji 反应
  6. dynamicPace() — 等待间隔（400-1500ms，基于文本长度）

clampSpokenReply 限制

// 按句子数限制（模板定义的 sentenceMax）
// 按字符数限制（模板定义的 charLimit）
// 过滤 "..." / "…" 等无意义回复 → return null

被动反应系统（Passive Reactions）

每条 AI 消息发出后，其他 AI 角色会概率性地添加 emoji 反应：

  • 检测消息情绪（funny/scary/sad/exciting/question/neutral）
  • 根据角色性格决定反应概率（0.08 ~ 0.32）
  • 受 GM 的 ENGAGEMENT 分数控制（1-5 档）
  • 每条消息最多 3 个反应
  • 延迟 800-3300ms 后显示

Typewriter 效果（AI 角色消息）

// game-pace.ts typewriterReveal()
addStreamingMessage({...}, channelId, "");    // 创建空消息
requestAnimationFrame(function tick() {
  pos += charsPerTick;  // 默认 3 字符/帧（~16ms/帧）
  updateStreamingMessage(messageId, text.slice(0, pos), pos >= text.length);
  if (pos < text.length) requestAnimationFrame(tick);
});
⚠️ requestAnimationFrame 在后台标签页不执行！如果用户切换标签页，typewriter 效果会暂停直到用户返回。这不会导致数据丢失，但会延迟消息显示完成。

消息显示流程

函数作用isStreaming

addStreamingMessage创建流式消息（初始内容为空）true
updateStreamingMessage更新流式消息内容isComplete ? false : true

如果 isComplete && !content.trim() → 显示 "…"

指令解析优先级

  1. splitHostOutput(raw) — 按 --- 分割为 message + directives
  2. getStreamingDisplay(raw) — 流式预览时剥离指令行
  3. parseHostResult(directives) — 解析 NEXT_SPEAKER, AUTO_CHANNEL, CHANNEL_GOAL
  4. parseRoleAssignments(content) — 解析 ASSIGN_ROLE, ELIMINATE, GAME_OVER
  5. parseHostActions(content) — 解析 BOARD, SECTION, MOOD, VOTE 等
  6. parseGmState(directives) — 提取 GM 大脑状态 JSON
  7. parseCharacterDirections(directives) — 提取角色指令

12. 已知问题 + 潜在风险

🔴 已修复的严重 Bug

Bug 1: isRoundInProgress 永远卡住（已修复）

  • 原因：callHostStream 的 fetch 没有超时，SSE 流可能永远挂着
  • 影响：后续所有消息走排队路径，AI 永远不回复
  • 修复：添加 45s fetch 超时 + 30s SSE 停滞检测 + 120s 全局看门狗

Bug 2: retry 路径无超时（已修复）

  • 原因：callHostStream 的 catch 块中，retry fetch 没有 AbortController
  • 影响：即使主请求超时了，retry 可以无限挂着
  • 修复：retry 也使用同一个 roundAbortRef 的 signal

Bug 3: 非 402 API 错误静默（已修复）

  • 原因：callHostStream 中 !res.ok 且非 402 时，直接返回空结果，无 toast
  • 影响：用户看不到任何错误提示
  • 修复：所有 API 错误都显示 toast

🟡 潜在风险（仍需关注）

风险 1: 消息上限 60 条

addMessage 和 addStreamingMessage 都限制消息总数 60 条。超过时会丢弃旧消息。如果 streaming 消息被丢弃，updateStreamingMessage 找不到它，更新会静默失败。

风险 2: pendingHumanMsgRef 只保留 1 条

在 isRoundInProgress 期间发送多条消息，只有最后一条会被保留和重放。之前的消息虽然显示在聊天中但不会触发 AI 回复。

风险 3: handleSendMessage 闭包捕获

handleSendMessage 不是 useCallback 包裹的，每次渲染都是新函数。它捕获当前渲染时的 gamePhase、isRoundInProgress 等值。由于 ChatInputArea 使用 handleSendRef.current（每次渲染更新），通常不会有问题，但在极端渲染竞争条件下可能使用旧值。

风险 4: typewriterReveal 使用 requestAnimationFrame

后台标签页中 requestAnimationFrame 不执行。如果用户在 AI 消息打字时切换标签页，返回后才能看到完成的消息。不会导致数据丢失，但体验可能困惑。

风险 5: /api/chat 无超时

非流式 /api/chat 路由没有 AbortController。如果 OpenAI API 挂了，await openai.chat.completions.create() 可能永远不返回。

影响：runPrivateChannelConversation 中的共识检查可能卡住整个 speaker queue。

缓解：已为 speaker-queue.ts 中的两个 fetch("/api/chat") 添加 30s 超时。但 route.ts 服务端本身没有超时。

风险 6: Scene 模式 openingSequence 延迟

launchOpeningRound 中播放 openingSequence 使用 await new Promise(r => setTimeout(r, msg.delay))。如果有很多条消息且 delay 很长，这会阻塞很久。如果用户中途离开页面，seedCancelledRef 可以中断。

风险 7: isMountedRef 检查

GameRoomContext 的 addMessage、addStreamingMessage、updateStreamingMessage 都检查 isMountedRef.current。如果组件卸载（如路由跳转），所有异步操作的消息更新都会被静默丢弃，但不会报错。

🔵 架构决策说明

为什么 isRoundInProgress 是 local state？

它只属于 useHostRound hook。不需要全局共享。如果组件卸载重新挂载，重置为 false 是正确的行为（旧的异步操作不再相关）。

为什么用 SSE 而不是 WebSocket？

GM 消息是单向流（服务器→客户端）。SSE 比 WebSocket 更简单，兼容 Vercel/Netlify 等无状态部署。Next.js API routes 原生支持 ReadableStream。

为什么消息上限 60 条？

防止 React 状态过大导致渲染变慢。游戏对话通常不需要回看很久以前的消息。GM 的 context window 只用最近 20 条（HOST_CONTEXT_WINDOW）。

为什么有 retry？

网络偶尔中断、OpenAI 偶尔超时。自动重试一次可以在大多数情况下恢复正常体验。
